# 00. 出発点と全体像

## 何が律速だったか

`novel-hoshiyomi` の第 6 話は、依頼者フィードバックの反映(Phase B/C)が 18 巡に達した。
2026-07-31〜08-02 の 3 日間に集中し、1 日 10 巡・6 時間の日があった。
話設計書 `第006話.md` は 157KB に膨らみ、その大半が指摘ログだった。
`novel-hoshiyomi` の最終コミットは 2026-08-02(ブリーフの「2026-08-06」とは食い違う。ローカルと `origin/main` の両方で確認した)。

指摘ログから読み取れる構造は次の 3 つ。

1. **機械で止められた指摘を人間が見つけていた。**
   語彙(`要注意語.tsv` に後から足された語)、句読点(`check.pl` の S4/FRAG)、同型文の連打、時間経過の標識文など。
   `write-episode` は「tsv を先に足す」「修正文を自己検査する」を手順として書いていたが、守られたかどうかを確かめる仕組みがなかった。
2. **会話で diff を往復する形が遅かった。**
   依頼者は 10 件ずつ区切って送り、毎回コミットせずに HEAD との diff をエディタで読んでいた。
   どの指摘がどの行に効いたかは設計書の散文ログにしか残らない。
3. **設定の照合が散文の全読みだった。**
   整合性レビュアーは封印資料と全話を毎回通読していた。
   キャラの知識状態や時系列は散文の中にあり、「第 N 話時点でこの人物はこれを知っているか」を機械で引けなかった。

設計はこの 3 つを潰す順に組む。
蓄積データ(本文、craft 文書、指摘台帳、採点台帳、指摘ログ)は使う。
仕組み(フェーズ制、tmux drive、会話での diff 提示、ChatGPT 反映)は引き継がない。

## 3 層の役割

```text
┌──────────────────────────── novel-atlas (public) ───────────────────────────┐
│ src/       PWA ビューア(React + Vite + Dexie + vite-plugin-pwa、GitHub Pages)│
│ src/core/  スキーマ(zod)・照合・lint。ブラウザと scripts の両方で使う          │
│ scripts/   照合 CI・隔離バンドル・なろう取得・索引生成                         │
│ .claude/   ルーティンが使うスキルとレビュアー定義(作品の中身を含まない)        │
│ 本文・設定・craft 文書は一切置かない                                          │
└──────────────────────────────────────────────────────────────────────────────┘
            │ 照合スクリプトを checkout して実行                ▲ PAT で読む・コメントする
            ▼                                                   │
┌──────────────────────── novel-atlas-data (private) ─────────────────────────┐
│ works/<作品>/  本文・話設計書・canon・feedback・採点                           │
│ craft/         共通層の craft 文書・共通 lint 辞書                             │
│ references/    他作品の本文キャッシュと解析結果                                 │
│ .github/workflows/  PR ごとの lint・canon 照合(必須チェック)                  │
└──────────────────────────────────────────────────────────────────────────────┘
            ▲ PR を開く・push・返信・マージ後同期
            │
┌──────────────────────── Claude のルーティン(claude.ai) ─────────────────────┐
│ 執筆 / コメント反映 / マージ後同期 / 他作品収集 / 他作品解析 / 見守り         │
│ Routines 画面から作り、両リポジトリを接続した新しいセッションで起動する        │
└──────────────────────────────────────────────────────────────────────────────┘
```

`shogi-atlas` から引き継ぐ運用規約:

- ルーティンは claude.ai の Routines 画面から作る。プロンプトは「スキルを読んで実行せよ」だけにし、手順はスキルに書く。
- GitHub 操作は `gh api`(REST)で行う。`gh issue` / `gh pr` は GraphQL を使うため使わない。
- 定期処理を private リポジトリの Actions に載せない(無料枠を消費する)。Actions は PR ごとの短い検査だけにする。
- ビューアは Fine-grained PAT で Contents API を読む。トークンをコードに埋めない。
- `novel-atlas` 本体の開発は Issue 駆動(`ready` → `in-progress`、`area:*` ラベル、`/work-issue`)。

## 設計の原則

- **人間が読むのは整った最終稿だけ。**
  機械で判定できるものは CI が止め、意見の割れる指摘は内部レビューが先に処理する。
  依頼者は物語として読み、好みと方向を返す。
- **判定は決定的に、抽出だけを LLM に。**
  「本文がこの事実を述べているか」の抽出は LLM が行い、結果を YAML として PR に残す。
  canon との一致判定はスクリプトが行う。結果が再現でき、誤りを抽出と判定のどちらで起きたか切り分けられる。
- **`確定` だけを硬く、`仮` は柔らかく。**
  `仮` との食い違いは警告に留め、CI を落とさない。背骨だけを固定する方針を維持する。
- **手順はファイルの状態で強制する。**
  「tsv を先に足す」はスキルの注意書きではなく、「`vocab` に分類した指摘に辞書行が無ければ CI が落ちる」で担保する。
- **1 話の記憶は PR に集める。**
  話設計書・本文・指摘・返信・CI 結果・採点が 1 本の PR に載る。マージ後は `feedback/` と canon に蒸留する。
